# Admin Supabase Integration Design

## Intent

Make Mini Shop's existing admin product and order screens operate on the configured Supabase project, and keep the customer storefront consistent with those records without changing its visual design.

## Verified current state

- Admin product management uses the hard-coded `PRODUCTS` array.
- Admin order management and checkout store order data in `localStorage`.
- The home and product-list pages already fetch active catalog rows from Supabase. Product detail, cart, favorites, and checkout still use hard-coded products.
- `products` includes `id`, `name`, `price_vnd`, `category_id`, `description`, `image_path`, `is_active`, `created_at`, and `updated_at`.
- `orders` includes `id`, `order_code`, customer fields, `status` (default `pending`), `total_vnd`, and `created_at`. Its ID is generated by identity.
- `order_items` references `orders.id` and `products.id`; it stores product-name and price snapshots.
- RLS is disabled on `categories`, `products`, `orders`, and `order_items`.
- Existing product images are under `public/MiniShop_Assets/assets/images/products/`.
- Admin authorization already trusts only the verified `app_metadata.role = "admin"` claim.

## Goals

- Add, edit, and archive products in Supabase. Confirm before archiving; archive with `is_active = false` so products disappear from the customer catalog while order history remains intact.
- Select existing product images or upload an image into public Supabase Storage, bucket `assets`, object path `download/<unique-filename>`. Store its public URL in `products.image_path`.
- Show persisted orders and their line items in admin, with guarded `pending → shipping → delivered` status transitions.
- Make customer home, list, detail, cart, favorites, and checkout resolve the same active Supabase catalog.
- Persist guest checkout to `orders` and `order_items` atomically, deriving names and prices from active database products rather than trusting browser totals.
- Use the same database-backed figures for the admin overview.

## Security and behavior

- Enable RLS on the four exposed public tables. Anonymous and authenticated customers can read categories and active products. Only admins can manage product rows and read order details.
- Admin server actions verify `app_metadata.role`; database RLS independently enforces admin permissions. Never expose a service-role key.
- Disallow direct public table writes to orders and order items. An intentionally narrow RPC accepts guest checkout input, validates it, calculates authoritative totals, and inserts the parent and child rows in one transaction. Revoke default `PUBLIC` execution and grant the RPC only to `anon` and `authenticated`.
- Enforce order status transitions both in server actions and RLS update policies. Admin order updates may change status only.
- Make bucket `assets` public for image retrieval, but allow uploads only to authenticated admins and only under `download/`. Use unique object names and do not overwrite or auto-delete shared images.
- Accept JPEG, PNG, and WebP uploads up to 6 MB. Keep existing static images in `public/MiniShop_Assets`; never write uploads into the deployed Next.js filesystem.
- Preserve guest checkout and add strict field, item-count, quantity, active-product, and price validation. CAPTCHA and a separate external rate-limiting service are out of scope for this iteration.
- Cart and favorites remain browser-stored product IDs. A catalog reload/navigation reflects product changes; Realtime subscriptions are not required.
- Do not create or modify production test orders or products. Verify code with mocked/unit tests and verify remote configuration with read-only metadata queries.

## Non-goals

- Redesigning the existing storefront or admin visual system.
- Category management, online payments, customer order-history accounts, or live Realtime updates.
- Changes to the original HTML/CSS/JavaScript project outside `mini-shop-next`.
